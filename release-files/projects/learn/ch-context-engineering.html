上下文工程：
压缩、刷新与前缀缓存

假设一个退货助手跑到第 40 轮对话，每轮输入从第一轮的约 3,200 个 词元（Token） 涨到 8,400 个，账单涨到约 2.6 倍。团队先在提示词上加了两段说明，账单纹丝不动。他们以为要改措辞，问题却出在历史与组装顺序上。预算（Budget）告诉我们一次调用能放多少，工程问题是怎么放。

打个比方，长对话像一本越写越厚的会议记录。逐字翻到第 40 轮又慢又贵，得把前情压成几页摘要，能复用的旧页就别重新誊一遍。

正式定义：上下文工程（Context Engineering）决定每一轮往上下文（Context）里放什么、拿掉什么、按什么顺序放。哪些内容压缩、哪些前缀可以缓存复用，也由它决定。历史会变长，压缩减少 token 数量，缓存省掉重复计算，两件事要分开记账。

速览

每次模型调用前，运行时（Runtime）里的组装模块（上下文构建器）要做四个决策：选什么、什么时候加载、用什么表示、保留多久。单次输入会随轮次线性增长；五轮调用的累计输入可达八万 tokens。压缩减少 token 数量，缓存省掉重复处理，两者收益方向不同但彼此牵制。

摘要若放在稳定前缀之内，每改一次，从改动处往后的缓存都要重新预热；把摘要放在易变部分，就不会连累前面的稳定前缀。

整理材料，比重复叮嘱更具体

用户说“按上次的格式做”，模型未必拿到了上次的文件。再加一句“认真一点”，仍然没有补上格式。小运（运行时程序）需要找到正确模板，确认它适用，再把必要段落放到当前输入里。

上下文工程要决定每次交给模型哪些材料，按什么顺序放，怎样压缩，何时更新。除了提示词，还要整理检索结果、历史摘要和工具返回。

用一页交接单压缩一次长任务

假设一次故障排查留下了很多日志。交接单可以记四件事：要解决的问题、已经验证的事实、排除过的解释、下一步要做的检查。原始日志仍保存，只有需要复核某一处时再读取。

接手的人读到“试过几个办法，都不行”，还得重新调查。若写成“重启后仍出现同一错误；尚未修改数据库；下一步检查连接超时”，他就知道哪些操作做过、下一步从哪里开始。

工具返回也可以先收窄范围。查订单只需要状态、更新时间和相关字段时，没有必要把整个用户档案都放进模型。少给无关信息，通常比事后要求模型忽略它更直接。

前缀缓存（Prefix Cache）解决的是重复计算。重复的材料如果满足缓存条件，可以少处理一部分。缓存只负责复用计算；材料是否正确、是否相关，要在组装时另行判断。

一份很短的摘要可能只保留故事梗概，丢掉约束、证据位置与未完成动作，反而更难继续任务。

机制

组装前的四个决策

四个决策是选择、时机、表示和保留。选择决定这次调用要哪些事实和指令。时机决定哪些现在加载，哪些等工具结果回来再加载。表示决定哪些需要精确结构与来源，哪些可以压缩成摘要。保留决定哪些留在下一次调用，哪些写进外部存储。

拿一次退货请求对照。选择只要三样：订单号、订单状态、退货政策里对应的一段。时机是先查订单，状态是「已发货」才去取政策。表示上订单用结构化字段，政策用原文段落。保留上，这两样下一轮还要用，历史里的寒暄直接丢掉。

四个决策会互相牵制。表示选错，后面很难补救：把订单状态写进一段自然语言摘要，下一轮要精确引用这个状态时，只能重新查。保留决策还决定写回哪里：会话状态放外部存储，下一次调用按需取回，输入里只留一个指针。

提前加载与按需加载

加载时机可以落到一个固定的排版上。稳定不变的部分放前面：通用指令、输出契约、工具目录、技能索引。容易变化的部分放后面：当前状态、相关历史、工具结果、本轮用户消息。原则是易变细节放最后。这个顺序同时服务前缀缓存：缓存比对的是 token 序列的前缀，稳定内容放前面才能被复用。

假设（示意）稳定部分合计 2,400 tokens，其中工具目录占 500，两个工具各 250；易变部分 800。第 40 轮时易变部分涨到 6,000，稳定部分还是 2,400。两段的位置关系决定了哪一截能复用。

反过来排会出事。把工具结果放在系统指令前面，每轮工具结果都不一样，前缀从第一个 token 起就变，缓存一次也命中不了。

这个顺序可以压成一句话：稳定的系统提示（System Prompt）和工具清单放前面，易变的用户请求、历史和工具结果放后面。工具清单本身也占预算。工具从 2 个加到 20 个，每个按 250 tokens 算，工具目录就从 500 涨到 5,000，稳定部分被它吃掉一大半。

历史为什么会膨胀

每一轮调用都要重发整段历史，所以单次输入随轮次线性增长；累计账单增长更快，近似按轮次平方。一个算例是：五次调用的新输入从 6K 涨到 26K，累计输入达到 80K tokens。

  1. 五次调用的新输入分别是 6K、11K、16K、21K、26K，每轮新增 5K。
  2. 累计输入是 6,000 + 11,000 + 16,000 + 21,000 + 26,000 = 80,000 tokens。
  3. 按每百万 2 美元算，一次五轮对话的输入成本是 80,000 × 2 / 1,000,000 = 0.16 美元。
  4. 一天一万次这样的对话，输入成本是 1,600 美元。

第三次调用的 16K 里，有 11K 是前两轮已经发过的内容。除了费用，长上下文本身还会让模型抓不住重点：证据放在两万字中间时，被用到的概率明显下降（推断）。

压缩：把长的变短

压缩的对象主要是对话历史。一个典型的例子：用户先说「取消 ORD-1001」，随后改口「其实别取消了」，最后只想查 ORD-1004 的退货资格。压缩后的摘要要留下四件事：没有执行写操作、当前任务是查资格、取消已撤销、下一步是资格查询。好的摘要保留修正、未完成工作和动作限制，不写成流水账。

常见的五种压缩手段各有适用面。选择保留相关的完整单元，结构化提取保留必需字段。摘要把长对话压成一段概述，检索加压缩从大集合里取紧凑摘录。学习式 token 过滤只留选中的词。

方法适用场景保留什么
选择多轮对话、多文档相关的完整单元
结构化提取大记录、长响应必需字段与精确事实
摘要长的早期对话一段更短的语义概述
检索加压缩大的外部集合相关、紧凑的摘录
学习式过滤冗长的来源文本选中的词或 token

压缩要算净收益。假设（示意）一段历史 5,000 tokens，摘要压到 800 tokens，之后还有五轮要重发。未来五轮相对不压缩，毛省（5,000 − 800）× 5 = 21,000 tokens，折合 0.042 美元。

生成摘要也有花费。压缩调用的 5,000 个输入 tokens 约 0.01 美元。800 个输出 tokens 按每百万 10 美元计，约 0.008 美元。两项合计 0.018 美元。

把这项成本扣掉，净省约 0.024 美元。

这五种手段可以叠加使用，但每一次压缩都会丢掉一些东西。压缩的边界就在这里：摘要写错比没有摘要更糟。一个教学反例是这种版本：摘要把「别取消了」写成「取消已处理」，助手下一轮照着摘要执行了取消。

触发时机也要定。等到历史占满输入再压，单次就压不完；定在占七成时动手，压完还有重试的余量。一次压太多同样危险，把还在一句话里的上下文切成两截，助手会接着错的前提往下答。

前缀缓存省的是重复处理

缓存和压缩解决的是两个问题。压缩让上下文变短，缓存让相同的上下文不重复计算。前缀缓存复用前几次调用的键值（Key-Value，KV）缓存。它能复用的前提，是序列化后的 token 前缀完全相同。语义相近但字面不同，命中不了。

算例还是五个请求、每个一万输入、公共前缀八千 tokens；第一个请求没有缓存可命中，按全价计（冷启动）。按输入每百万 2 美元、命中按一成计价。

T_miss 与 T_hit 是未命中、命中的 token 数，α 是命中折扣，p 是每百万 token 的原价。代 T_miss=18,000、T_hit=32,000、α=0.1、p=2，得到 0.0424 美元。

  1. 不缓存：五个请求共 50,000 tokens，成本 50,000 × 2 / 1,000,000 = 0.1000 美元。
  2. 启用复用：首个请求全部未命中，10,000 tokens；后四个请求每个命中公共前缀 8,000、未命中 2,000。
  3. 未命中合计 10,000 + 4 × 2,000 = 18,000 tokens，按原价是 0.036 美元。
  4. 命中合计 4 × 8,000 = 32,000 tokens。按一成计价，32,000 × 0.2 / 1,000,000 = 0.0064 美元。
  5. 总成本 0.036 + 0.0064 = 0.0424 美元，下降 (0.1000 − 0.0424) / 0.1000 = 57.6%。
  6. token 加权命中率是 32,000 / 50,000 = 64%。

如图 5.1 所示，命中的三万多 token 按一成计价，输入成本从 $0.1000 降到 $0.0424（约 4.24 美分）。

这也解释了一个常见故障。把一条新规则插到系统指令中间，从插入点往后的整段前缀失效；插入点之前还可以复用。缓存按 token 序列比对前缀，稳定内容一旦挪位置，复用就断了。

成本与限制

压缩有信息损失。把早期对话摘要成四行，可能丢掉后来才用上的细节。压缩调用只付一次，省下的重发费用随轮次累加；被丢掉的信息会在之后某一轮变成错误回答。压缩本身还有延迟，一次摘要调用按 1.2 秒算，30 轮里做 6 次就是 7 秒多。

缓存有失效成本。容器重启、模型版本切换、排版变动都会让前缀失效。两者还要配合：摘要若在稳定前缀里，改了它就要重新预热后面的缓存，而预热的那一次调用按全价计；把摘要移到易变部分，就不会连累前缀。缓存本身也占资源：前缀越长，留在显存（GPU Memory）里的副本越大，按 GB 计的显存要和省下的钱一起算。

这套工程不适合所有场景。一次性的单轮问答既不需要压缩，也吃不到缓存收益。窗口足够大、任务又不长的场景，直接按顺序拼上下文更省事。按本章假设（命中一成计价、首次原价），同一段前缀第二次起就省钱；实际要看供应商是否另收写入费、缓存多久过期。

自测

  1. 四个决策里，哪一个决定了「哪些内容等工具结果回来再加载」？
  2. 五次调用累计 80K tokens 的算例说明了什么？
  3. 前缀缓存的命中条件是什么？语义相近的前缀为什么命不中？
  4. 用正文数字重算：五个请求各一万输入、公共前缀八千、首个冷启动、命中按一成计价，总成本是多少？成本下降多少百分比？
