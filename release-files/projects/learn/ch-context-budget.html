上下文预算：
一次推理里装什么

假设一个客服助手在第六轮对话里答错了一句：客户问退货期限，它答「7 天」，而政策上周已经改成 15 天。日志显示这次调用的输入已经接近 7,000 个 词元（Token），证据就在库里，没进模型的眼睛。装得下只是容量；装得对还要看内容，窗口怎么分、证据怎么挑，需要一笔一笔算清楚。

打个比方，上下文（Context）像一张有限大的桌面。能摊开的纸有上限，而且桌上放的还得是当下用得上的那张；最新政策锁在柜子里，桌上再满也帮不上忙。

正式定义：上下文（Context）是一次模型调用收到的全部输入，包括指令、历史、当前请求、工具说明、证据和记忆。上下文窗口（Context Window）是它最多能装的 token 总数；上下文预算（Budget）就是在这块有限空间里，决定放什么、拿掉什么。

速览

上下文（Context）是一次推理调用（Inference）中模型收到的全部输入，包括指令、历史、当前请求、工具定义、证据、记忆与技能。上下文是这一次送进模型的内容；窗口是它最多能装多少 token；上下文预算是怎样在窗口里分配内容。

预算把窗口拆成七项：六项输入（也就是上下文）加一项生成预留；七项相加不能超过窗口，并且必须先扣掉输出预留。容量够只是第一关；相关性差和证据过期同样会让回答失败。三项检查的失败方式不同，要分开做。

把上下文看成一次会面的材料

小模每次作判断前，都要收到一份当前材料。它可能包括任务、规则、聊天历史、工具说明和新查到的结果。这份材料叫上下文。系统保存过的资料，只有被取出并放进本次输入，才会影响这次计算。

把上下文想成一张桌面：它能摊开的纸有限，而且放上来的纸还得有用。桌上堆着很多文件，最新政策却留在柜子里，小模仍然无从知道那个关键日期。桌面只用来比喻当前输入的容量。

图 4.1 的总窗口为 8,192 个词元。先为输出留 1,024，输入最多使用 7,168；两段按实际比例画出。容量足够后，还要检查材料是否相关、版本是否有效。

先保留做决定离不开的信息

如果输入材料合计 9,000 个词元，就超过 7,168 的输入上限，至少要减少 1,832 个。小运（运行时程序）先去掉重复日志和已经排除的候选，保留用户约束、当前决定与证据。删掉唯一的预约编号虽然也能腾地方，却可能让后续核验失去依据。这是教学假设，真实服务还可能有独立的输入、输出或计费限制。

整理完后，可以请另一个人只看留下的材料：他能找到订单号吗？知道用户允许改什么吗？能接着上次失败的位置查下去吗？答不上来，就要把相应记录补回去。

长上下文模型也会漏用输入中的信息。信息放得下，只说明通过容量检查。研究提示，证据在长输入里的位置会影响被使用的概率，放在中间比放在开头或结尾更容易被忽略（推断）；所以越关键的约束，越应在组装输入时前置或重复，并通过改动事实、检查引用和结果来验证。

机制

上下文是这一次调用的输入

这个概念在这里定义得很窄：上下文是一次推理调用中模型收到的全部信息。数据库里的行、记忆库里的记录，只有被搬进模型输入才起作用。

工程上能控制的是「模型这次看到什么」；「系统知道什么」要经过组装才进入计算。订单记录在 SQLite 里存了三年，模型这一轮看到的是那 300 个 token 的字段快照。同一份记录被复述进对话历史后，可能膨胀成 600 tokens 的一句话，中间夹着模型自己的解释。

这条界线还能解释一类事故。客户三个月前改过收货地址，库里是新的，但这次拼上下文时只取了订单行的旧字段，模型照着旧地址回答。问题出在组装：新地址没有进这次调用。

七项预算与一次减法

预算公式把窗口拆成七项：前六项构成输入（上下文），分别是指令 I、历史 H、当前请求 U、工具定义 T、证据 E、记忆与技能 M；第七项是生成预留 Y。七项相加不能超过窗口 W。

I+H+U+T+E+M+Y≤WI + H + U + T + E + M + Y \le WI+H+U+T+E+M+Y≤W

七项的单位都是 token。W 是模型配置里的窗口上限，Y 必须先留出来。

代号内容订单助手里对应什么
I指令与示例系统提示、四类意图说明
H历史前几轮问答
U当前请求「我的订单到哪了」
T工具定义查订单、查政策两个参数定义（schema，参数字段说明）
E证据数据库回来的订单记录
M记忆与技能客户偏好、启用中的技能
Y生成预留留给模型输出的空间
W可用窗口模型配置里那个上限

表里最后一行 W 是窗口上限；真正相加的是前七行（I 到 Y）。生成预留不能省。输出是逐 token 生成的，预留不够会让回答在中途被截断。窗口 8,192 tokens、预留 1,024 tokens，输入预算就是 8,192 − 1,024 = 7,168 tokens。

这条减法的边界在余量怎么用。把 7,168 全部塞满，输入是够了，回答却只剩 1,024 个 token 的空间；中文一段话按每字 1.5 个 token 估，大约 680 字。长回答、表格、代码都会吃穿这个数。

工具定义常常被低估。假设助手挂了 20 个工具，每个定义连同说明约 250 tokens。光这一项就是 5,000 tokens，已经占去 7,168 token 输入预算的大半。工具越多，留给历史和证据的地方越少。

把订单助手摊开算一遍

假设这个助手的输入分配如下（数字为示意）。系统指令与意图说明约 600 tokens，前五轮历史约 2,000，工具定义约 900。订单记录约 300，用户当前那句话约 40，记忆与技能这一轮是 0，生成预留 1,024。

  1. 六项输入加总：600 + 2,000 + 40 + 900 + 300 + 0 = 3,840 tokens。
  2. 输入上限是 7,168，剩余额度是 7,168 − 3,840 = 3,328 tokens。
  3. 换一种算法核对：六项加预留 3,840 + 1,024 = 4,864，8,192 − 4,864 = 3,328，两种算法一致。

剩下的 3,328 tokens 能放什么，取决于证据有多大。假设每段配送政策约 1,600 tokens（大约一千字），两段占 3,200，还剩 128。第三段再占 1,600，三段政策合计 4,800；六项输入变成 3,840 + 4,800 = 8,640，超出输入上限 7,168 的额度 1,472。

这笔账的意义在于暴露取舍。第三段要不要放是取舍问题。若试图从生成预留里再挪出 1,472 tokens，原有 1,024 tokens 根本不够。此时预算无效，服务可能拒绝请求或截断输入；应先减少材料，或在服务允许的范围内调整限额。

不放，又可能答不出「超过 5 天要转人工」这条规则。

顺带算一下钱。输入六项合计 3,840 tokens，1,024 的预留是给输出留的空间，输出按实际生成量另算。按每百万 2 美元算，一轮输入约 0.0077 美元，一天一万轮约 77 美元。这个数在下一章会被前缀缓存（Prefix Cache）改写。

三项检查彼此独立

这里的“独立”指判据独立：容量、相关性、新鲜度各自回答不同问题，一项通过，另一项仍可能失败。组装过程中可以先估算已有材料，取回候选证据后再核算实际长度；三项检查都通过，才把输入交给模型。

容量只是第一道检查。它问的是七项加起来有没有超窗口。相关性检查问放进去的是不是这次要用的，新鲜度检查问证据是不是当前版本。

三项的失败方式不同。输入超限时，服务可能拒绝请求或截断输入；输出预留用尽，则可能使回答在中途结束。相关性或新鲜度不足，回答仍可能流畅，却使用了错误材料（推断）。

检查时先记录实际输入长度，再核对证据的对象与版本。同一个问题两次答对，只覆盖这两次；输入选择是否可靠，还要换问题与证据版本再测。更新政策后答错，可以沿检索结果、缓存版本和模型引用继续查，确认新政策是否真的进入并被正确使用。

失败案例各有一个。新鲜度：政策从 7 天改成 15 天，模型还在读缓存里的旧段落，回答流畅地错。相关性：拼上下文时把另一个客户的订单记录带了进来，模型照着别人的订单状态回答，答得越顺，泄露越多。

三项检查只管输入有没有资格进来；模型怎么使用输入，是另一层问题。三项都通过，模型仍可能选错证据、把 300 的订单号抄成 800。

容量要按实际组装的材料核算。例如已有输入就超过上限时，可以先裁剪；检索出新证据后，仍须重新计数。相关性和版本检查仍要做。

四个操作决定怎么腾地方

这里把整理上下文的操作分为四类。选择（Select）决定这次取哪些证据，结构化（Structure）用消息角色和类型化结果区分来源。压缩（Reduce）裁剪或摘要中间内容，刷新（Refresh）在数据过期时重查。这四类是预算不够时的应急操作；下一章的四个决策是每次组装前的常规判断，分属两组。

选择决定取哪些材料，结构化区分来源与类型；压缩减少长度，刷新则解决资料过期的问题。举个组合的例子。订单状态用结构化结果放进工具角色的消息，历史里的闲聊压成一句摘要。政策文档改成按关键词检索一段，价格与库存每次现查。

选择要看目的。客户问退货，订单详情里的商品图片、优惠明细都不必进上下文，取订单号、状态、下单时间三项就够。这三项大约 40 tokens，而整行记录是 300。结构化要标来源，模型才能分清哪段是用户说的、哪段是工具返回的。

压缩的边界是信息损失。把五轮对话压成四行，可能丢掉后来才用上的细节。刷新的代价是延迟，每次重查多一次数据库往返，按 0.4 秒算，五轮就是两秒。

成本与限制

预算思路的代价是组装成本。每次调用前都要重新计算占用、做取舍、写回日志，这比把整段文本丢给模型贵。一轮多花几十毫秒，一天一万轮就多花几分钟的机器时间。

估算本身也会错。真正按分词器（Tokenizer）算，得到的是精确值；组装前常用每字 1.5 个 token 之类的经验值估。假设实际是每字 1.8，一段 2,000 字的政策就比预估多 600 tokens。余量不足时需要重新裁剪或调整请求，不能假定服务会自动保住关键内容。

窗口设得太紧会挤掉仍然影响任务的旧事实，设得太松则让关键证据被无关内容淹没（推断）。它还催生一种偷懒做法：每次都把所有材料塞进去，靠窗口够大兜底。缓存与费用的账会很快找上门。

它还有一类不适用的情况。如果任务只有一次问答、材料也短，把文本按顺序拼好就够了，做预算分配反而增加复杂度。预算真正开始值钱，是在多轮任务里上下文反复逼近上限的时候。

自测

  1. 预算公式的七项分别是什么，为什么要先扣掉生成预留？
  2. 容量、相关性、新鲜度三项检查各自会被什么现象暴露？
  3. 订单助手剩 3,328 tokens 时，为什么「全放三段政策」是个错误决定？
  4. 用正文数字重算：六项输入 3,840 tokens、预留 1,024、窗口 8,192，剩余额度是多少？若每段政策 1,600 tokens，两段之后还剩多少？
