工具：
契约、约束解码与 MCP

假设一次查订单的调用失败了三次。模型每次都把参数写成 order_id: 1002，主机的校验每次都说「参数无效」。模型不知道错在哪，只能换个写法再试，第三次把订单号填成了 ORD-1002A。参数格式、说明文字、错误返回，三者一起决定一次调用能不能成。

打个比方，工具契约（Tool Contract）像一张填好的订餐单：写清店名、要哪几栏、每栏填什么、成功和退单分别怎么回执。模型和程序都照这张单子对接，谁也不用猜对方的规矩。

正式定义：工具契约（Tool Contract）是工具名称、参数、返回值和错误格式的约定。模型按它生成请求，程序按它检查和执行；双方都认这份约定，调用才能稳定跑通。

速览

一个工具的最小契约由名称、输入 模式定义（Schema）（一份参数说明）和执行结果三部分组成；描述和错误格式也要写进契约。模型能看到名字、描述和参数 schema，返回格式通过工具结果体现。校验和执行都在主机侧完成。这里的主机（Host）指承载运行时（Runtime）的应用。

运行时至少要过四道检查：JSON 语法、schema 与类型、是否允许、权限与前置条件。约束解码（Constrained Decoding）把非法 词元（Token） 在生成时就屏蔽掉；语法通过之后，请求是否合理还要主机检查。模型上下文协议（Model Context Protocol）标准化发现和调用；权限仍留在主机。

一张表单怎样变成工具调用

订餐表单会把地址、份数和备注分开填写。工具契约也在做类似的事：明确工具叫什么，需要哪些字段，字段能填什么，成功与失败分别返回什么。

小模生成调用请求，小运（运行时程序）检查后执行。reserve_room 只是请求里的工具名称，背后还要有实现预约的代码、可用的连接和执行权限。

格式正确，仍然可能办错事

假设工具需要日期、起始时间和时长。日期必须符合格式，是第一层检查；结束时间不能早于开始时间，是业务检查；当前用户能否预约这间房，是权限检查。三者都要由程序落实。

模型可能把“下周五”转换成一个合法但错误的日期。字段类型检查无法发现这种错误，还要把解析结果与用户请求核对。写操作尤其需要在提交前展示关键参数，让用户能够发现偏差。

遇到“权限不足”，下一步可能要询问授权；遇到“服务超时”，则要核对结果并判断能否重试。若接口只返回“失败”，这两种情况就混在了一起。契约应写清错误类型、请求编号和是否允许重试。

模型上下文协议解决工具如何被发现与调用的连接问题。工具是否安全、权限够不够，仍由应用自己的检查负责；接上统一接口之后，业务责任仍属于提供服务的系统。

返回合法的结构化数据，只说明格式通过。预约是否正确，还要检查日期、对象、权限和实际写入结果。

机制

契约有三块

工具契约的最小形态，是名称、输入 schema（描述参数类型、必填项与格式的结构化说明）和执行结果。这是最小三块；完整的契约还要有描述和错误格式。订单助手的 lookup_order 收一个 order_id，返回订单状态或 not_found。

模型能看到名字、描述和参数 schema；执行结果和错误码通过工具返回体现。它不知道数据库在哪，也没有权限。

{"name": "lookup_order",
 "parameters": {"type": "object",
   "properties": {"order_id": {"type": "string",
     "pattern": "^ORD-[0-9]{4}$"}},
   "required": ["order_id"],
   "additionalProperties": false}}

schema 里的 pattern 是有意义的。它把可接受的输入收窄成 ORD 加四位数字，ORD-1002 合法，1002 和 ORD-1002A 都不合法。补零写法 ORD-0000 到 ORD-9999 一共一万个字符串能通过这一条，大小写不在允许范围内，ord-1002 也过不去。

契约同时约束两端：模型照着它写调用，主机照着它做校验。左边是可执行的函数，右边是模型看得见的说明。两边写的是同一件事，对不上的部分就是事故来源。

描述文字也属于契约。同一句「查询订单」写得含糊，模型可能把订单号和快递单号混用。工具描述里写清「按订单号查，订单号形如 ORD-1002」，这句话本身就是一次校验，能省掉一批参数错误。

执行结果也是契约的一部分。返回 {"order_id": "ORD-1002", "status": "shipped"}，模型能按字段取值；返回一句「处理中，已经六天了」，模型只能把整句抄进回答，下一轮想引用状态值就没东西可引。约定错误也要结构化，not_found、forbidden、timeout 分别对应重试、交人、等一会儿，混成一个 error 字段，模型只能猜。

图 6.2 先看参数格式：ORD-1002 符合约定，1002 不符合。格式通过之后，主机仍须查询订单是否存在，并核验当前用户能否读取；这些业务事实无法单靠 schema 判断。

调用是模型写的，执行是主机做的

模型输出的调用表示可以是文本，也可以是结构化 JSON。以朴素 JSON 协议为例，模型返回一个带 kind 和 name 的对象，终态是 final 或 ask_user。主机收到后要过四道检查。这四道依次是 JSON 语法、schema 与类型、动作是否被允许、权限与前置条件。

四道检查各拦一类错法。括号少一个，第一道拦。order_id 写成数字 1002，第二道拦。本次运行只读，模型却要调退款，第三道拦。订单属于别人，第四道拦。

四道检查写在主机代码里。提示词里写一句「只允许查询」，模型可能照做，也可能不照做；真正的限制在主机代码。

四道全过才进入分发（Dispatch）器。分发器按显式映射找到对应函数执行，不按模型给的名字直接调用。执行结果按角色为 tool 的消息追加回对话，再触发一次模型调用。模型提出动作，主机校验并执行，结果作为观察写回，下一轮输入随之更新；这四件事构成下一次决策的输入。

量一下这四道的效果（数字为假设）。这里假设四类错误互不重叠，且每次调用最多犯一类。一天 10,000 次调用，格式错误 300 次，类型错误 200 次，越权动作 50 次，权限不足 20 次。真正执行的是 10,000 − 300 − 200 − 50 − 20 = 9,430 次。被拦下的 570 次里，越权的 50 次和权限不足的 20 次，若没有检查就可能变成真实写入。

失败案例出在错误信息上。四道检查只返回「失败」两个字，模型没有线索，就在同一个参数上重复两三次；如果返回「order_id 必须是 ORD 加四位数字，你给的是 1002」，模型下一次基本能改对。校验的价值一半在拦截，一半在把错误说清楚。

如图 6.3 所示，五段里主机侧占了两道闸：校验与分发，任何一道不过都不该执行。

约束解码

格式也可以在生成阶段就保证。常见做法分三层。生成前用提示词声明只返回一个 JSON 对象，生成中按语法屏蔽非法续写。生成后由运行时解析和校验。

屏蔽的做法是给候选 token 打分。假设当前已经写到 order_id 的值的数字部分，后面只能是数字。为简化，把候选收窄到四个：1002 和 10 合法，oops 和右引号非法、概率记为零；合法的两个 logit 设为 3 和 2。

这里把 1002 当成一个整体候选，是为了简化；真实分词器（Tokenizer）可能把它拆成多个 token。logits 就是第 3 章那个还没过 softmax 的原始分数。

取指数得 20.09 与 7.39，总和 27.47，两项分到 0.731 和 0.269。

这个算例的意义在候选空间。词表五万，屏蔽前每个位置都有五万个候选；进入数字位后，如果分词器把每个数字当独立 token，合法候选只剩十个数字，概率全部压在这十个上；真实分词器也可能把多位数字合成一个 token，合法候选会更多。约束越强，模型越不容易跑偏。

约束的层级从语法到取值依次收紧。最外层是完整 JSON，往内依次是工具与参数形状、参数类型、枚举取值、正则模式。SGLang 的跳步优化在论文的测试设置下报告过 JSON 解码（Decoding）吞吐提升；具体倍数随语法与负载变化。

它的边界有两处。语法层只能挡住形状，ORD-9999 格式完全合法，至于这个订单存不存在、属不属于当前用户，要在主机侧查。把 pattern 收得过窄也会挡人：新订单号改成 ORD-1002A 之后，旧正则会把全部合法请求拒掉。生成后才发现的格式错误还要整轮重来，多付一次输入与输出。

部署方式与模型上下文协议

工具的实现可以放在三个地方。第一种是本地函数，简单好调试，但和进程耦合，慢调用会拖住整个助手。假设下游一次调用要 8 秒，并发只有 1；在这 8 秒里又来了 9 个请求，它们只能排队。如果这些请求等不到结果就结束，前面已经付过的输入 token 不会退。

第二种是远端服务，通过超文本传输协议（HyperText Transfer Protocol，HTTP）暴露。远端服务把数据和规则留在服务端，代价是要维护认证、作用域和版本。它还要处理重试：一次失败重试两次，下游压力按三倍算。

第三种是模型上下文协议（Model Context Protocol，MCP）。它把工具发现和调用做成统一接口。名字里的“上下文（Context）”指模型与工具之间的交互上下文；第 4 章的上下文窗口（Context Window）是另一回事。

价值可以用适配次数算：假设 3 个工具要接进 5 个助手。各自定制要写 3 × 5 = 15 份适配；统一协议之后，工具侧写 3 份服务端，助手侧写 5 份客户端，合计 8 份。

MCP 这一层只规定交换格式。服务端暴露 tools/list 和 tools/call 两个接口，客户端把结果交回主机。权限策略仍然由主机决定：能不能调、能调哪个用户的订单，都由主机检查。

成本与限制

契约给得越细，模型的自由度越低。正则写得太窄会把合法输入挡在外面，写得太宽等于没写。版本不同步也会让调用失败。例如工具新增了必填字段，主机已经更新，客户端缓存的参数说明却没刷新。模型仍按旧 schema 填参数，每次都会漏掉新字段。

约束解码需要维护语法状态机。实际耗时取决于语法复杂度、解码实现和硬件，可以用同一批任务比较。

更危险的是把格式正确当成语义正确。schema 保证字段齐全、类型对、模式匹配；订单是否存在、属于谁、当前用户有没有权限，都要主机另查。

还有一类成本在排障上。一次被四道检查拦下的调用，日志里要能看出拦在哪一道、参数长什么样。缺了这段记录，团队只能看到「调用失败」四个字。
