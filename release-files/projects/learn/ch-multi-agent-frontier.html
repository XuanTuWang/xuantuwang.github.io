多智能体、计算机使用与生成式 agent

一个研究任务有 100 篇论文要读（教学设想）。如果材料超出单次可处理范围，可以换一种组织方式：5 个 Agent（智能体，下同）各读 20 篇，各自写出发现，最后合并。这类任务把问题从单机循环推到了协同、界面与生成三种形态。三种形态看着不同，底层都是循环加工具，差别在循环的数量与接口的形态。

打个比方：多智能体（Multi-Agent）像把一项大任务拆给几个同事分头查再汇总；计算机使用（Computer Use）像让 Agent 直接看屏幕、点鼠标；生成式 Agent（Generative Agent） 像让它从脚本到成片一路产出。三者共用同一套循环和工具，只是分工方式和操作入口不同。

正式定义：多智能体（Multi-Agent）指多个 Agent 分工协作，各自有上下文（Context）和预算（Budget）；计算机使用（Computer Use）指让 Agent 看屏幕、点鼠标、敲键盘操作软件；生成式 Agent 指能生成文本、图像、视频等内容，也可结合工具完成任务。

速览

多智能体把任务拆开并行做，收益来自并行搜索与上下文分摊（每个 Agent 只读一部分材料），代价是协调与一致性。计算机使用把屏幕当通用接口，单步成功率会随步数复利衰减。生成式 Agent 把长内容拆成索引、检索与渲染，用中间指标检查每一步。三种形态的共同瓶颈都在错误累积与验证。

多个执行者需要怎样一起工作

把研究一份旅行计划拆成交通、住宿和活动，三个部分可以独立查资料。但它们还要使用同一日期、同一预算和同一组旅客约束。多智能体系统的难点常常落在交接与合并上。

主 Agent（负责分派与合并）拆分任务时，要把每份工作的范围写清。执行者（工作 Agent）交回结果时，附上依据、未解决的问题和重要假设。最后还得核对这些结果能否组成同一份旅行计划。

先有单个执行者的基线

多找几个模型同时作答，会增加覆盖，也会增加重复、矛盾与费用。一个错误假设如果被共享给所有执行者，可能得到许多一致的错误回答。意见一致不能替代独立证据。

独立核对可以采用不同资料或不同检查方法。比如一个执行者整理候选场地，另一个按用户约束核验表格；最终仍读预约系统状态。这样的分工比让多个模型互相赞同更可检查。

计算机使用把行动入口换成了界面。模型通过截图或页面结构观察，再提出点击、输入与滚动。页面可能移动、按钮可能失效，因此动作之后要重新观察。识别出按钮只是找到位置；按下后是否成功，要重新观察。

从找视频到做视频

多模态任务还要区分检索现有片段与生成新画面。前者需要保存原始时间位置与内容证据；后者需要管理脚本、镜头、素材和生成结果之间的一致性。两者都可以由 Agent 组织，验收条件却不同。

比较这些方法时，先固定任务目标和预算，再看单执行者、多执行者以及不同操作界面的实际完成率。结果中还应保留交接和操作界面带来的失败。

三个执行者给出相同结论，未必比一个可靠。还要检查它们是否共用了同一错误来源，以及结果能否被外部记录独立核验。

机制

多智能体的三个难点

多智能体要解决三件事：任务怎么拆、上下文怎么传、协调怎么可靠。最难的是第三件，因为错误会在 Agent 之间累积。比如一个执行者把错误日期写进共享状态，另外两个按这个日期查资料，最后三份结果一致地错；因为大家读的是同一份记录，错误被放大了。

举例：100 篇论文分给 5 个 Agent，每人 20 篇。拆得动，是因为论文之间基本独立。如果任务是一条前后依赖的流水线，并行反而增加返工。

任务分解的质量决定上限。拆得太粗，Agent 之间还要二次沟通；拆得太细，交接次数上升。

一种做法是让主 Agent 自己选工作流（Workflow）。固定流程是计划、分派、复核三步；现在由主 Agent 决定这一步该委派还是自己做。运行时（Runtime）负责传递调用与结果、保存共享状态、执行权限与预算；控制器（Controller）在运行时里管停止条件（Stop Condition）。

交接时最容易丢的是三样：任务目标、已完成的部分、预算归属（这次调用算谁的 词元（Token） 额度）。写清这三样，比多传几句对话有用。

一条设计经验是：模型越强，固定编排可以越少。这里指编排流程变轻；边界与预算仍由运行时执行，验收由独立评估（Evaluation）器或人负责。

如图 23.1 所示，任务在 Agent 之间交接，主 Agent 负责分派与合并；这张图画的是子代理模式，团队模式和工作流模式的拓扑不同。

长程编程任务常分成从零构建、加功能、修缺陷与重构四类。拆给多个 Agent 的价值在并行探索，代价是 token 与协调成本。

新观察会改变下一步，主 Agent 要在合并时重新检查各分支是否还对齐目标。

失败案例：两个 Agent 拿到重叠的子任务，各自改同一个文件。合并时冲突，返工的成本超过并行省下的时间。拆任务时要先定边界与合并规则。

组织方式决定协调成本

多智能体有三种组织方式。子代理模式把一件聚焦的小事委托出去，结果回到主 Agent；团队模式让队友各负责一个方向，共享发现；工作流模式把阶段写死，阶段内部由 Agent 自由选择。

共享记录是协调的关键。一个 Agent 写下改动、结果与证据，另一个 Agent 在下次试验前先读，避免重复踩坑。

并行试验是另一个用法。三个 Agent 各试一个方向，算力分开跑，结果齐了再进入依赖步骤。团队模式还需要一个共同的进度视图，否则不同方向跑着跑着就分叉了。

规模可以很大，但价值取决于任务本身的并行度。多智能体的价值在有用的多样性；重复的想法再多也没有用。

收益会递减。协调开销随 Agent 数量上升，任务本身的并行度却有限。先测串行的瓶颈，再决定要不要拆。

计算机使用：四层接口与单步复利

计算机使用的前提是没有可用接口，只有屏幕。能接触系统的方式有四层：调用函数、执行命令、读页面结构、看像素。越靠上（越接近函数调用）越精确，越靠下（越接近像素）越通用。

如图 23.2 所示，四层从上到下依次是调用函数、执行命令、读页面结构、看屏幕。能走高层就不要落到像素层，这是成本原则。

界面信号要合起来用。只看像素容易点偏，只看结构会被大量无关节点淹没。做法是先读结构找到可点的控件，再用坐标或视觉定位去点，点完重新读页面确认。以页面上的确认状态为准，例如看到「已预订」才算成功；看到错误提示就回退。

结构给出名字与位置，像素给出兜底。两者缺一，密集界面上的点击就会漂移。

单步成功率会复利。单步 95% 时，20 步全对的概率是 0.95²⁰≈0.36，即 36%。真实任务的步数可能远多于演示，每步的可靠性比平均分更值得看。

P20=0.9520≈0.358P_{20} = 0.95^{20} \approx 0.358P20​=0.9520≈0.358

P_20 是连续 20 步都成功的概率。单步成功率每降一点，指数会把差距放大。这个乘法假设每一步相互独立；真实任务里错误可能相关，36% 只能当量级。

手机更难：不少应用不暴露可靠的页面结构，系统对第三方应用的命令与接口限制也更严。所以今天的手机 Agent 大多仍主要靠看屏幕，辅以系统提供的无障碍结构信息。

手机还有隐私问题，屏幕离开设备，云端每收一步都是一次上传。

两个公开评测覆盖了这两类环境；具体分数随版本与任务集变化，比较时要按同一口径重跑。

失败案例：一次误点可能结束整轮（教学例子）。桌面误点可能覆盖文件或发出邮件，没有撤销；手机上 Agent 也判断不了自己走错了，因为通常只有下一屏，没有可回读的确认记录（订单号、状态页）。

生成式 Agent：检索与渲染

生成式 Agent 处理长内容。剪辑类任务先建索引。按固定时间窗切片，给每片生成画面描述与语音转写。再按请求扩写成有序分镜，逐段检索并裁剪对位。

索引本身要花算力与时间。切分、描述与转写都在请求前完成，换来的是检索时的低成本。

评估看中间结果。检索召回率（Recall）看有没有找对片段；嵌入（Embedding）相似度把片段描述和请求都变成向量（Vector），看余弦相似度，只判断「像」；片段是否「对」，要看召回与交并比。这三个指标对应三个环节，任何一个环节错了，后面的渲染都救不回来。

举例：目标时段是 4 秒到 8.5 秒，选中 3.5 秒到 5.5 秒。重叠是 4 秒到 5.5 秒，共 1.5 秒；并集是 3.5 秒到 8.5 秒，共 5 秒；交并比是 1.5÷5=30%。

IoU=∣A∩B∣∣A∪B∣=1.55=0.30\mathrm{IoU} = \frac{|A\cap B|}{|A\cup B|} = \frac{1.5}{5} = 0.30IoU=∣A∪B∣∣A∩B∣​=51.5​=0.30

A 是目标时段，B 是选中时段，分子是重叠长度，分母是并集长度。

生成类任务的方向相反：从想法生成镜头。它先写脚本与角色，再拆镜头、定机位（镜头从哪个位置拍）、选关键帧，最后逐镜头生成。调度按依赖关系安排：例如镜头 5 的机位依赖镜头 2 的场景布置，但镜头 3、4 可以先渲染。依赖图决定哪些镜头能并行。

为演示依赖调度，假设同一故事生成任务串行要 835 秒，重排（Reranking）后要 405 秒；任务规模设为 35 个故事、438 个镜头。这些数字是教学算例，不来自论文或公开榜单。算例保持模型不变，只比较调度方式；真实任务的收益要另测。

单次生成还有时长上限。更长的片子靠扩展与拼接，拼接点是角色与场景最容易崩的地方。

最难的是保持一致。镜头之间的角色与场景要保持一致，靠特征相似度检查。一致性分数是相似度，用来比较镜头之间像不像；质量仍要人看。

检索分只覆盖片段找得对不对；成片好不好，节奏与叙事仍要人看。

成本与限制

多智能体的协调成本是真实的。每个 Agent 都要读上下文、写结果，交接本身要花 token。任务拆得太细，协调开销会吃掉并行收益。

计算机使用有三类固定代价：每步都要付费、一次误点就结束整轮、屏幕内容会离开设备。前两条影响成本与成功率，第三条影响合规。

延迟也随步数线性增长。12 步就是 12 张截图、12 次调用与 12 次上传，每一步都要重新读页面。

生成式 Agent 的指标容易误读。召回率只说明检索对不对；成片好不好看要另评。口径不一致时，数字也会互相打架：同一任务按调用数、按任务数、按用户数算，成本能差几倍。

评估要分层。协同看合并后的结果，界面看每一步能否恢复，生成看中间产物。

还有一条经验判断：能力曲线比信任曲线陡。任务完成率涨得很快，无人值守的授权边界没有同步涨；这是经验判断，还没有测量数据。
