持久状态、崩溃窗口与恢复对账

考虑这样一次故障：凌晨两点，账本导入任务跑到第 7,000 行时机器重启。重启后系统面对一个具体问题：第 7,000 行到底写进账本了没有。日志里只有一条「开始执行」，文件里可能已经有这条记录。判断错了，要么少一行数据，要么多出一行重复。

打个比方，持久状态（Persistent State）像一本任务进度簿。每做一步先记“打算做什么”，做完再记“做成了什么”。中途断电重启，翻着这本簿子对账（Reconciliation），就知道哪些事真做过、哪些要重来。

正式定义：持久状态（Persistent State）是存到磁盘、进程重启后还能恢复的运行状态。配套做法是执行前先写意图、执行后写结果，日志只追加；重启后拿当前状态和意图逐条对账，再决定记成功、重放（Replay）还是交人工。

速览

崩溃窗口（Crash Window）指动作已经提交、结果还没记录的那一小段时间。做法是执行前先写意图，执行后写结果，日志只追加。重启后拿当前状态和意图对比，判断动作是否已生效，再决定记成功、重放还是停下交人工。

回滚、文件恢复和业务补偿改的是三个不同的层，各有自己的适用范围。恢复能做对，要么动作可安全重放任意多次（幂等），要么每次重放前能查到外部状态。

电脑关掉以后，任务还剩下什么

写文章时只存在编辑器里的段落，断电后可能丢失。保存到文件之后，下一次才能继续。智能体（Agent） 的任务状态也需要保存，只保留模型当前输入（也就是上下文（Context））通常不足以支持恢复。

恢复比“重新问一遍”更复杂。模型可能再次选择同一个动作，而这个动作已经在外部发生。预约、发邮件、创建工单都需要区分正在尝试、已完成和结果未知。

一张已经发出的通知怎样恢复

假设小运先发送通知，随后记录“发送成功”，但恰好在中间崩溃。重启后没有成功记录，只说明本地还没确认；小运应当根据请求编号查询邮件或通知服务，再决定如何补记。

小运也可以在行动前先存下准备发送的内容和对象，成功后再记结果。即使中途崩溃，恢复时也知道要核对哪次发送。不过，意图记录和成功记录之间仍可能出现空隙。

检查点（Checkpoint）像一本任务簿的书签，标明已确认的进度。恢复时可以从书签附近重放计算，不过涉及外部写入的步骤必须有去重、查询或补偿办法。检查点只覆盖本地进度；外部写入要靠这些办法保证只执行一次。

回滚也分层。恢复一份本地文件，可能只需版本记录；撤销一封已送达的邮件，未必有对应操作。写恢复流程时，要逐项确认能撤销哪些操作，哪些操作只能在事后补救。

没有成功日志，通常只说明本地尚未确认；外部结果仍可能需要对账。

机制

崩溃窗口落在两次写之间

动作可能已经生效，结果还没写进日志。文件改完了，进程在这时掉电，重启后没人知道这次改动做没做。这段时间落在哪里，如图 15.1 所示。

async def execute_checked(self, call):
    action = self.validate_and_authorize(call)
    if action.kind == "file_edit":
        intent = self.plan_versioned_edit(action)
        self.record("intent", intent)     # 先记意图：要做什么
    try:
        out = await self.execute(action)
    except Exception as exc:
        out = f"ERROR: {exc}"
    self.record("result", call, out)      # 后记结果：做成了什么
    return out

这段代码的顺序要逐行看。授权在写入之前，意图在动作之前，结果在动作之后，异常也被写成一条结果。

但这段代码只以文件编辑为例：发通知、转账这类动作也要在执行前记意图；示例还省略了授权结果的记录。更关键的是，进程崩溃不会走到 record("result")，日志会缺结果条目，缺的正是「动作到底生效没有」这条信息。日志供恢复流程读，模型不一定看；上下文是这一次发给模型的输入。

窗口有多窄，算一笔账就清楚。假设每个动作写盘 1 毫秒，写一条日志 0.2 毫秒，一次运行 100 个动作。逐条记日志时，日志总耗时 100×0.2 等于 20 毫秒，单次窗口约 0.2 毫秒。

只要业务写入和日志写入不在同一个原子操作里，窗口就存在，只是宽窄不同。窗口大小不只看日志怎么写，还看业务写入有没有真正落盘；日志说成功、业务数据还在缓存里，崩溃后也会丢。

Tlog=100×0.2=20 ms,W≈0.2 msT_{\text{log}} = 100 \times 0.2 = 20\text{ ms}, \qquad W \approx 0.2\text{ ms}Tlog​=100×0.2=20 ms,W≈0.2 ms

T_log 是日志总耗时，W 是单次动作的崩溃窗口。窗口不随日志总耗时一起缩小，它由业务写入和日志写入之间的间隔决定；单条日志怎么写，只是其中一半。

把动作和结果放进一个事务（Transaction），能不能消掉窗口，要看动作落在哪里。动作落在业务库、日志落在日志文件，两个系统没有共享事务，仍有窗口。如果两者都在同一个数据库，可以用一个事务保证原子；但发邮件、调第三方这类外部副作用不在事务里，仍然要靠意图和对账。

先记意图，再记结果

意图要写到「恢复时能核对」的粒度。以账本导入器为例，补丁的意图可以写成：把编号 1001 和 1002 的重复行合并，预期记录数从 4 变成 2。这条意图包含动作、对象和预期结果，重启后能拿来和文件比对。

结果要包含成功、失败和超时三种。异常也要落成一条结果记录，写成 ERROR 加原因；超时也记成一种失败结果，别让它变成空白。把异常吞掉、只留一个空白的 result 字段，会让恢复流程以为动作没执行。

记录意图的时机在授权之后。授权判定本身也可能改变文件，例如建目录、写锁，所以授权结果也要记一条，恢复时才说得清是谁放行的；示例代码省略了这条记录，实际实现要补上。

版本化编辑把改动变成可核对的数据。补丁在执行前先算成一份具体改动，包含基准（Benchmark）版本、目标文件和替换后内容的指纹（Hash，用于比较内容是否相同）。恢复时不用重新推演，只检查文件当前内容是否等于「基准加改动」。相等说明动作已经生效，不等就比较差异，差异在允许范围内才重放。

版本号比时间戳可靠。文件时间戳在恢复、复制、同步时会被改写，内容指纹只由内容决定；文件相同，指纹应当相同。

意图写太细，恢复要跑很多核对步骤；写太粗，又判断不出动作做没做。粒度应该落在“能幂等地重放”这个尺度上：重放任意多次，效果和一次相同。

重启后的对账看状态

重启时执行恢复流程。对账就是拿保存的意图和当前状态逐条比对，判断动作是否已生效。它把当前文件状态和已保存的意图做对比，分三种情况处理。

第一种，预期改动已经在文件里。账本是 2 条记录、两个编号各出现 1 次，和意图一致。这时记一条成功结果，继续往下走，不重放。核对依据也要留下来，例如文件内容指纹，下次恢复不用重算。

第二种，动作没有生效。账本还是 4 条记录、两个编号各出现 2 次。这时重放补丁，再记结果。

第三种，状态和意图对不上。账本是 2 条记录，但编号是 1001 和 1003。这时不要猜，停下来交人工审查。

判断依据是当前状态；时间戳只说明记录顺序。时间戳写得很全、状态没核对，恢复照样出错。

日志只追加，重放要幂等

日志只追加，不改写。追加写避免覆盖旧记录，但崩溃可能留下半条尾部记录；每条记录带长度或校验和，恢复时丢弃不完整的尾记录，再按顺序回放。每条记录至少带动作标识、策略决策和结果，否则恢复时判断不了前因。

日志要和业务数据分开存放，还是放在同一个事务里，取决于你要哪种保证。同一个事务保原子性：要么都写、要么都不写；但业务数据损坏时，日志也可能一起坏。

分开存放保独立性：业务库坏了日志还在；但两者可能不一致，要靠对账补。两种做法各有代价，要按需要的保证选。无论选哪种，日志本身都要定期归档，否则长任务的日志会比数据增长更快；归档之前要保证对账读得到意图本身，恢复只关心最近未完成的那些意图。

重放的前提是幂等。幂等指重放任意多次，效果和一次相同。动作本身仍可能执行多次，外部副作用要靠去重键保证不重复，例如用订单号加动作类型作为唯一键，重复写入直接忽略。

会话树与三种回滚

历史被组织成只追加的树。每个节点记一条消息和它的父节点，回滚到某个节点只是不再采用后续分支，记录本身仍保留。探索在从某个节点分出的分叉支路（Fork）上进行，不覆盖原历史。需要比较两条路线时，这样做的成本比复制整个工作区低。节点最好带版本号，回退时能一并找到当时的工具版本。

回滚要分清三件事。历史回退改的是记录，文件恢复改的是磁盘状态，业务补偿改的是已经发生的外部影响；业务补偿就是用一个反向动作抵消影响，例如退款、撤回或发更正。判断一次崩溃该做哪一件，取决于动作的影响落在哪一层。

失败案例：重放把一条通知发了两遍

发通知的动作在提交成功后掉电，日志里没有结果记录。恢复流程看到「意图存在、结果缺失」，判断动作没执行，直接重放。用户收到两封内容相同的通知。

换成转账、下单、删除文件，同类错误会造成更大的后果。解决办法有两个：给动作加幂等键，或者在重放前先查外部状态。外部状态查不到时，通常要停下来交人工，让「可能重复」的风险留在明处。

另一个失败更隐蔽。对账只看日志时间戳，发现最后一条记录是「开始执行」，就把它记成成功。实际上文件还是 4 条重复记录，验收却被跳过，账本带着错误继续往下走。

成本与限制

日志的成本是每个动作多一次写盘。高频小动作上这笔开销很明显。批量写能压成本，代价是把崩溃窗口拉宽。上面的例子里，每 100 条批量一次；每个动作写盘 1 毫秒，所以两次批量写之间约 100 毫秒，窗口最长约 100 毫秒，是逐条 0.2 毫秒窗口的 500 倍。

批量写本身假设为 0.2 毫秒，另算。算总耗时要先定口径：是每条日志 0.2 毫秒，还是每批 0.2 毫秒；两种算法的结果不同，报告里要写清。

对账只能处理可检查的副作用。转账、发消息、第三方下单这类动作，外部系统不一定给查状态，对账就退回人工。动作的影响跨多个外部系统、状态散落在第三方后台时，核对成本可能高于重做一次。

外部状态查询也会超时，超时按「可能已执行」处理，宁可交人工确认。

恢复流程本身的成本也被低估。每次重启都要扫一遍未完成的意图，扫得越细越慢。意图积压多了，重启可能从秒级变成分钟级。

重放日志本身也要幂等。恢复流程重启一次就把日志写重复，对账的输入就不干净了。

意图的粒度没有统一答案，取决于动作能否幂等重放。动作本身不幂等时，先改造动作，再谈恢复，顺序反了会把恢复流程变成事故来源。

自测

  1. 崩溃窗口具体落在哪两次写之间？
  2. 每个动作写盘 1 毫秒、每条日志 0.2 毫秒，一次运行 200 个动作。逐条记日志与每 50 条批量记一次，日志耗时各是多少？批量时最坏窗口有多长（假设一次批量写盘同样耗时 0.2 毫秒）？
  3. 重启对账的三种情况分别怎么处理？
  4. 重放为什么会把一条通知发两遍？除了查外部状态，还能怎么防？
