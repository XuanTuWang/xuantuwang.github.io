运行时控制器：
预算、停止与验收回路

在账本导入的教学例子里，同一批表格数据被导了两次，出现了重复流水号。小模看完代码说已经修好，控制台也打印了成功。重跑之后，账本里还是 4 条记录，而期望是 2 条。系统该采信谁，小模的自评还是重跑的结果？

打个比方，控制器（Controller）像项目里的交付把关人。模型说“我做完了”不算数，它要核对预算（Budget）还剩多少、验收是否通过，再决定放行还是打回去重改。

正式定义：运行时（Runtime）控制器（Controller）是运行时里管预算和停止的部分。模型可以提议停止，控制器用预算账和验收器（Verifier）结论判断能不能接受；验收不过就把失败报告写回上下文（Context），让模型接着改。

速览

控制器是这一轮运行里管预算和停止的裁决者；策略检查、工具执行和验收由各自的模块负责。模型可以提议停止，控制器用预算账和验收器（Verifier）返回的结论判断能不能接受。

验收不过，控制器把失败报告写回上下文，让模型接着改。预算耗尽就停下，并给出一个明确的停止原因。一次运行结束时必须落到具体状态，例如完成、未完成或资源耗尽。这是本课程的教学约定；不同框架可以把这些职责拆成不同组件，无论怎么拆，预算和停止都要有负责人。

谁在模型犹豫时守住任务

小模连续多轮提议继续查，但它不执行查询。小运是运行程序，负责执行查询、把结果写进运行卡；控制器是小运身上管预算和停止的那部分，在下一轮开始前检查还剩多少轮、多少钱。模型外面的这套执行环境叫运行时（Runtime）。

订房任务里，小模提议查哪个房间。小运先问策略层这次动作是否允许，再确认工具是否可用；控制器只检查预算和轮次。这些检查都由程序执行，换模型后也要保留。

用一张运行卡记录进度

一张简化的运行卡可以记录任务目标、当前步骤、剩余预算、等待中的动作和停止原因；它是本书对“运行状态记录”的称呼，行业里没有统一的词。小运收到工具结果后更新运行卡，再组装下一次输入。这里的上下文，指下一次真正发给小模的输入；运行卡是运行时保存的状态，日志是事后记录。

验收失败的报告只有写进下一次输入，小模才看得到。

假设最多允许三次查询，当前已经用完两次。要不要把最后一次用在核对关键事实上，由小模提议、编排器（Orchestrator）判断值不值得；控制器只检查预算是否允许。

如果这次查询只是重复同一条已知结果，编排器可以决定不再查，让小模基于已有证据作答；查询值不值得由编排器判断，控制器只看预算。这是教学设计，实际限额取决于任务。

预算耗尽与任务完成需要不同的返回。前者应说明哪些问题仍没有答案，保存可以继续工作的进度。后者应给出完成条件与对应结果。把两者都显示为“已结束”，用户就很难理解发生了什么。

运行时还要处理模型以外的中断：网络断开、用户补充要求、外部接口报错。能恢复的依据来自保存的状态；后续章节的持久化、日志与检查点（Checkpoint），都是为了让这张运行卡在重启后还能读回来。

预算上限是系统实施的约束，要在每次行动之前判断；换一个更聪明的模型，这条检查仍然保留。

机制

控制器与编排器分工

这些组件各管一件事。控制器检查预算与停止条件（Stop Condition），编排器安排下一阶段走哪条、交给谁。策略层判断动作是否允许，工具执行器负责执行，验收器检查结果是否符合完成条件。

同一个进程可以承担多个职责，检查仍应分别落实。否则编排器可能一直安排下一步，绕过控制器设置的轮次上限。

图 12.1 只展开一次工具往返：输入交给模型，模型提出请求，运行时检查授权后调用工具，再保存并写回结果。控制器检查每轮预算与停止条件；策略检查决定动作能否执行，沙箱（Sandbox）进一步限制执行范围。

常规检查依据是预算账与验收器结论，用户取消或等待输入则作为单独事件处理。模型输出「已完成」时，控制器仍须核对验收结果。验收标准是否合理，需要由设计与评估（Evaluation）环节检查。

预算要按最坏情况判

账本导入任务给这次运行设了两条上限：最多 4 个模型轮次，总花费 1 美元。每轮开始前检查一次：轮次已满，或「已花费加下一轮最坏花费」会超过上限，就返回同一个资源类停止原因。

def _check_limits(self, worst_next_cost):
    # 轮次已满，或已花费加下一轮最坏花费会超过上限，都不放行
    if self.n_turns >= self.max_turns:
        return "BUDGET_EXHAUSTED"
    if self.cost + worst_next_cost > self.max_cost:
        return "BUDGET_EXHAUSTED"
    return None

这个检查有一个容易漏的边界。假设已经花了 0.98 美元，上限 1 美元，下一轮最坏会花 0.11 美元。按最坏情况算，这一轮不该放行，因为一旦花掉就是 1.09 美元，超出上限。按平均花费算，一轮可能只要 0.011 美元，看起来还有余量。

两种算法的差别在风险偏好：如果承诺硬上限，就按最坏情况判；如果允许透支，要明确写出来，否则“上限”只是事后统计。

平均 0.011 美元可以拆开算。一次调用输入 3,000 词元（Token），按每百万 2 美元算约 0.006 美元。输出 500 tokens，按每百万 10 美元算 0.005 美元，两项合计约 0.011 美元。

最坏情况的 0.11 美元，是把一次调用放大到输入 30,000 tokens、输出 5,000 tokens 的结果。预算检查要防的正是这种放大。0.11 只是单次调用上限；如果一轮允许 k 次重试，这一轮的最坏成本要按 (k+1)×0.11 算，重试不能靠“另留一点余量”拍脑袋。

Cworst=30,000106×2+5,000106×10=0.11 美元C_{\text{worst}} = \frac{30{,}000}{10^6}\times 2 + \frac{5{,}000}{10^6}\times 10 = 0.11\text{ 美元}Cworst​=10630,000​×2+1065,000​×10=0.11 美元

30,000 与 5,000 是放大后的输入、输出 token，2 与 10 是每百万 token 的单价。

预算还有一层用法：把剩余预算分给剩余轮次。4 轮、1 美元，平均每轮 0.25 美元，足够覆盖最坏情况。如果前两轮花了 0.6 美元，后两轮平均只剩 0.2 美元；0.2 仍高于下一轮最坏的 0.11，可以继续。只有当平均额度低于下一轮最坏成本时，才需要降级或收口。

停止原因是一组枚举值

停止原因是预先定义好的一组固定取值，也就是一组枚举值。它分成四类：完成、未完成、资源耗尽、系统故障。

类型状态含义
完成COMPLETED验收检查全部通过
未完成BLOCKED需要输入、权限或修复，当前拿不到
未完成CANCELLED用户或上层任务主动停止
资源BUDGET_EXHAUSTED达到轮次或费用上限
系统TOOL_FAILURE工具持续失败，无法继续
系统MALFORMED_OUTPUT修复次数用尽仍无法解析
系统INFRA_FAILURE基础设施故障，运行中断

分类的用处体现在后续处置上。BUDGET_EXHAUSTED 可以在运行状态还在时追加预算接着跑。MALFORMED_OUTPUT 要换模型或改工具契约（Tool Contract）。BLOCKED 要等人补输入，CANCELLED 则不该再自动重启。如果所有失败都写成一个字符串，调用方没法判断该重试还是该停。

枚举值还让失败统计变简单。一批任务跑完，按状态分组计数，就能看出失败集中在哪一类。如果 BUDGET_EXHAUSTED 占比很高，问题多半在预算定得太紧；如果 MALFORMED_OUTPUT 占比高，问题在输出格式或解析器。

外环验收

模型提议停止时，控制器先看预算；预算允许，再调用独立的验收器。验收通过才返回 COMPLETED；不通过，控制器把失败报告写回下一次输入，继续循环。验收器负责判断结果，控制器负责决定停不停。

账本导入的例子可以看清这一环。小模第一次修复后，运行时重跑导入，账本里还是 4 条记录，期望是 2 条。验收器返回失败，并给出具体断言：记录条数应为 2、流水号应唯一。控制器把这份报告写回对话，小模据此发现自己的去重逻辑只处理了相邻行，改成按流水号全局去重，第二次重跑得到 2 条记录。

验收断言要能自动执行；断言就是一段能自动判真假的检查。写「修好了」不算断言，写「导入后记录条数为 2」才算。断言越具体，反馈越有用；断言太笼统，小模只能猜。

账本任务的断言可以拆成三条：记录条数等于 2、流水号无重复、金额合计与原表一致。三条都是可执行语句，任一条失败就返回对应的失败原因。

这一环也会失败。一个常见的实现缺陷是验收失败的报告没有被写回对话，只是记在日志里。

模型下一轮看到的上下文和上一轮一样，于是重复同一个修法，验收器再验一次、再失败一次，直到轮次耗尽。表面上模型在努力，实际在空转。排查这类问题要看两轮之间上下文有没有变化；变化只在日志里而不在消息里，就是写回漏了。

执行状态与用户输入

一次运行在四个状态之间移动：执行中、等待、检查中、已结束。等待覆盖两种情况：等工具返回和等用户输入。预算检查在每轮开始前，所以预算耗尽会从执行中直接进入已结束；验收不通过则带着失败报告回到执行中。

图里从执行中分出两条路：调工具进入等待，产出候选答案进入检查；检查不通过带着失败报告回到执行，验收通过进入已结束。预算耗尽则在每轮开始前判定，可能从执行中直接进入已结束。

用户输入只在模型轮次之间的显式边界注入。任务跑到一半，用户又发来一句话，这句话不能直接插进当前轮次的上下文，要在下一轮开始时作为新输入加入。普通补充可以排队；如果用户要改目标或取消，走取消或重规划路径，不能等到当前任务验收完才处理。

常见实现包括线性循环、异步事件和有序中间件。它们分别按轮次执行、由完成事件唤起，或在每轮前后挂接检查函数。控制要点相同，一次运行选其中一种就够了。混用两套调度会让同一轮调用两次模型，预算被重复扣减。

成本与限制

验收回路的第一笔成本是每次停止都多跑一遍断言。断言要读数据库、比对结果，一次可能几百毫秒。任务很短时，验收的耗时可能超过任务本身。所以验收断言要按风险分级，关键结果用重断言，过程产物用轻断言。

断言要跟着业务改。十个任务各三条断言，就是三十条要维护的语句，业务规则一变，其中几条就要跟着改。没有维护的断言会慢慢变成噪音：它拦不住新错误，还会误报旧错误。

断言写错是两个方向的坑。写得太松，验收器会放行错误结果，账本还是 4 条却返回 COMPLETED；写得太紧，模型反复改同一个点，直到预算耗尽。两侧都可以用历史失败案例校准：把已知会失败的任务放进回归集，断言必须能拦住它们。

验收标准本身错了，控制器发现不了。如果验收只检查文件存在、不检查内容，验收器会放行，控制器也会返回完成。这类问题要靠更细的验收用例和人工抽检补，业务判断不在控制器。

还有一类任务不适合带验收回路的长循环。输出无法自动检查、人工复核又比写断言便宜时，一次生成加人工审更划算。带验收回路的运行适合结果可自动判定、失败可重试的任务。

自测

  1. 控制器和编排器各自拥有什么？为什么不能合并成一个角色？
  2. 已花 0.98 美元、上限 1 美元，下一轮最坏花 0.11 美元、平均花 0.011 美元。按最坏情况判和按平均判，分别得到什么结论？哪一种更适合硬上限？
  3. COMPLETED 和 BUDGET_EXHAUSTED 在后续处置上有什么区别？
  4. 验收失败后模型连续两轮做同样的修复，最可能是什么环节出了问题？该查什么？
